# Change 08.5 — Hardening (diagnostics, offer restrictions, quality checks)

Status: Complete

## Goal
Close three gaps found before the assistant (change 9):
1. **Diagnostics**: a failed operation can be traced from the `requestId` the user sees to the backend's log lines and the provider call that caused it. Today the backend never configures logging (its `INFO` lines, such as each provider call, are lost under uvicorn), the request id is not written to any log line, and an unexpected error does not return the standard error body.
2. **Offer restrictions** (US-03, the provider contract): the contract's optional `Offer.restrictions` (for example "Non-refundable simulated booking") is shown in search, in the booking confirmation, in the itinerary and in documents. Today the mock never returns it and the application ignores it.
3. **Quality checks**: a linter for the Python code and a type check for the frontend, each with one documented command, so "practical quality checks suited to the stack" exist and pass.

## Scope
- Backend (`backend/`): logging setup, request id in every log line, one access log line per request, a handler for unexpected errors; restrictions in the provider client, search, quote, itinerary (stored on the item, migration) and the document snapshot and PDF.
- Provider mock (`mock_provider/`): restrictions in the fixture offers and in every offer response (including the offer copied into a booking), as the contract shows.
- Frontend (`frontend/`): restrictions in the Search results, the booking confirmation dialog and the Itinerary; a `typecheck` script.
- Tooling: `ruff` for `backend/` and `mock_provider/`, with its configuration in each service; existing findings fixed.
- Tests, README and `PROJECT.md` updates.

## Out of scope
- Log shipping, metrics, tracing systems (OpenTelemetry and similar), structured JSON logs. Plain text lines with the request id are enough for this scope.
- A CI pipeline (GitHub Actions or similar): the checks are documented commands; CI is mentioned as part of the deployment approach in change 10.
- `mypy` or other Python type checking, ESLint, Prettier, frontend automated tests (documented limit).
- Filtering or sorting search results by restriction; restrictions that change prices or block bookings (they are information from the provider, shown as is).
- Changing `assignment/openAPI.json` (unchanged). The mock's `/control` endpoints are not used by the application. `assignment/` is read-only reference.

## Assumptions to confirm
- **Logging setup**: the backend configures logging at startup with the same format as the worker (`time level logger message`), level from `LOG_LEVEL` (default `INFO`, in `.env.example`). The worker uses the same setup function.
- **Request id in logs**: the request id created by the existing middleware is stored in a context variable and added to every log line written while handling that request (`request_id=req-...`). Lines outside a request (worker, startup) show `-`.
- **Access line**: one line per request after it finishes: method, path, status, duration in ms, request id and the user id when logged in. Health checks (`/health`, `/health/ready`) are not logged, to keep the log readable.
- **Provider calls**: the existing provider log line keeps the provider's own `X-Request-Id` and now also carries our request id, so one line links both sides. The contract defines no request-id header to send to the provider, so none is sent.
- **Unexpected errors**: any unhandled exception returns `500` with the standard body (`code: INTERNAL_ERROR`, a generic message, `requestId`), and the full traceback is logged with that request id. No internal details are sent to the browser.
- **Restrictions in the mock**: each fixture offer gets zero or more restrictions (for example "Non-refundable simulated booking", "Photo ID required at check-in", "Minimum age 18", "Carry-on bag only"), at least one offer per category has none, and the field is always returned as a list (empty when there are none). Changing an offer through `/control` keeps its restrictions.
- **Restrictions in the application**: the provider client reads `restrictions` as an optional list (missing means empty), and passes it through search results and the quote. An itinerary item stores the restrictions of the offer it was copied from (new column, a list; existing items get an empty list). "Refresh price" also refreshes them. The confirmation dialog shows the current restrictions and highlights them if they differ from the saved ones, like price and availability. The document snapshot and PDF include each item's restrictions. "No restrictions stated by the provider" is shown when the list is empty.
- **Ruff**: added to `requirements.txt` of both Python services (next to pytest), with a short configuration (default rules plus import sorting, line length matching the code, `tests/` included). Commands: `docker compose exec backend ruff check .` and `docker compose exec mock_provider ruff check .`. Existing findings are fixed in this change; no rule is disabled just to pass without a one-line reason.
- **Frontend type check**: a `typecheck` script (`tsc -b`) in `package.json`; command `docker compose exec frontend npm run typecheck`.

## Acceptance criteria
- Forcing a provider failure and then searching in the browser shows an error with a request id; `docker compose logs backend | grep <requestId>` shows the access line and the provider call line for that request, with the provider's status and its own request id.
- An unexpected backend error returns the standard error body with a `requestId`, never a bare `Internal Server Error`, and the traceback in the log carries the same id.
- Search results show each offer's restrictions; the booking dialog shows them and highlights a change; itinerary items and new documents show the restrictions saved with the item.
- `docker compose exec backend ruff check .`, `docker compose exec mock_provider ruff check .` and `docker compose exec frontend npm run typecheck` all pass.
- `docker compose exec backend pytest` and `docker compose exec mock_provider pytest` pass, including the new tests.
- `assignment/` is untouched and `openAPI.json` unchanged.

## Technologies implemented
- ruff (Python linter, in `backend/` and `mock_provider/`): the quality check for the Python code, with import sorting; one command per service.
- `typecheck` script (`tsc -b`) in `frontend/`: the quality check for the frontend (TypeScript was already a dependency).
